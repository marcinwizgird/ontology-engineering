Onboarding · Agentic Systems Engineering

ASE Team Handbook

ASE takes a written specification and produces an engineered, analysed and optimised agentic system. This handbook explains why it exists, how it is built, where it is going, and the rules everyone on the team works by.

Sources: CLAUDE.md, docs/ROADMAP.md, models/*.sysml, methodology/*.sysml, docs/ase-agent-factory.pdf (business briefing, October 2026). State as of 28 October 2026, increment I0 delivered.

What ASE is

ASE is an agent factory. A client's requirements go in as a specification. ASE consolidates them, picks a proven design from a pattern library, models the design in SysML v2, proves its properties with automated checks, gets a human decision, generates the code, evaluates it, optimises it and, from increment I4, deploys it.

"The goal is to produce agents the way a plant produces parts: from a library of proven designs, through a fixed routing, with inspection at every station." (business briefing)

Three assets serve that aim, and when priorities conflict, ASE wins:

PRIMARY

ASE Agentic System

The factory itself: models, analysis, code generation, the workbench app, the MCP server.

FEEDS ASE

Pattern knowledge base

The SysML v2 pattern library, the methodology and catalogue, the knowledge graph, and the skill library. ASE selects designs from it; ASE runs feed gaps back into it.

USES ASE

ASE School

An advanced course in agentic architecture engineering. Every module ships a real production asset; "the coursework is the factory build".

Business philosophy

The business case rests on one observation: most companies need the same few kinds of agent, and they need them built, checked and maintained reliably rather than invented each time.

The product is five agent types, not industries

Document Q&ADocument checkerTriage & routerException handlerReport drafter

Each type is a pattern family in the library. A new client is a new specification for an existing type, not a new project from scratch.

The economic lever is fleet maintenance

"A fix to a template, a security patch or a model upgrade is made once. ASE then regenerates every affected agent, re-runs its tests and redeploys only those that pass." That only works because generated code is deterministic and every agent has its own evals.

Who it is for

  • Mid-sized companies, including those on smaller ERPs (Business Central, Odoo, Sage, Epicor), as well as large ones.
  • A partner channel: ERP resellers and managed IT providers who need "a repeatable, tested product they can resell without an AI team".

Commitments to clients

Vendor-neutral

"The LLM provider is configuration." Generated code uses open frameworks (LangGraph, DSPy), so the client owns it.

Governance by design

"The audit trail is a by-product of production, not extra work." Every decision is a recorded graph node.

Nothing ships untested

An agent is deployed only after it passes evals tied to the client's own requirements.

Engineering principles

These rules are not style preferences. Tests and review enforce them, and a change that breaks one is rejected however good it is otherwise.

Six non-negotiables

1

Controls are read-only

The pattern library (models/rag-patterns.sysml), methodology/ and the skill library are obeyed, never edited by an ASE run. Gaps become an @Extension on the design, with a reason. A passing spec with a dirty models/ diff is a failing spec. Promotion into the library is a human commit.

2

ASE is modelled in ASE

models/ase-system.sysml describes ASE's own agents, flows and budgets in the same vocabulary it uses for clients. The orchestrator is generated from it, and selftest proves they match.

3

Every decision has a record

Pattern choice, waiver, deferral, assumption, optimiser acceptance: each is a graph node with owner, date, reason and the requirement it affects. "ASE drafts options and revisions; it never ratifies one."

4

Generated artifacts are never edited

generated/ and ASE School/notebooks/ are build outputs. Change the generator, then regenerate.

5

Skills live in one place

Only in AI Skills/skills/. Architecture skills map to the methodology and are read through the ase MCP tools.

6

Provider-agnostic

The model is chosen by SYSMLAGENTS_MODEL (a provider/model string) through dspy.LM or a LangChain factory. No provider SDK in pipeline, agent or codegen code. Offline paths work with no key.

The production contract

ASE's output is a deployed agent, not a source file. Three rules make that repeatable:

  1. Code is deterministic. Same design, same library version, same generator version gives a byte-identical program and deployment package.
  2. What a model produces is governed, not deterministic. Eval datasets and optimised prompts are versioned artifacts with seed, model, input hashes and approver. A regenerated artifact is a new version, never an overwrite.
  3. Nothing is deployed that has not passed its evals. The deploy gate reads the requirement thresholds and the held-out verdict.

Where the model decides, and where it doesn't

Deterministic where the model determines the answer: code generation, analysis, traceability, evidence packs, deployment, and deciding what is missing from a spec. Model-driven where it does not: wording elicitation questions, writing rationale, composing new designs, synthesising datasets, writing instructions.

The method

ASE follows the Architecture Definition Process of Rozanski and Woods (Software Systems Architecture, 2nd ed., ch. 7), expressed as an IDEF0 model in methodology/ase-process-idef0.sysml. Every ASE step realises one activity.

flowchart LR
  A1["A1 Consolidate the inputs"] --> A2["A2 Identify scenarios"]
  A2 --> A3["A3 Identify relevant styles"]
  A3 --> A4["A4 Produce candidate architecture"]
  A4 --> A5["A5 Explore options"]
  A5 --> A6{"A6 Evaluate with stakeholders"}
  A6 -- rework --> A7["A7 Rework the architecture"]
  A6 -- revisit --> A8["A8 Revisit the requirements"]
  A7 --> A5
  A8 --> A5
  A6 -- accepted --> R1["R1 Realise: code, evaluate, optimise, deploy"]

IDEF0 separates inputs (consumed; you may transform them) from controls (governing; not yours to change). Viewpoints, perspectives and the pattern catalogue are controls. This one distinction drives the read-only rule.

ASE modelled in ASE

models/ase-system.sysml describes the target workbench, AseWorkbench, in the same vocabulary as client designs. Each agent appears twice: as a leaf stage with aggregate numbers, and as its own pipeline. The self-test asserts the two agree.

flowchart LR
  L[SpecLoader] --> I[IntakeAgent]
  I --> S[ScenarioAgent] --> P[PatternAgent] --> D[DesignAgent]
  D --> M[(Materialiser)] --> AN[AnalysisAgent] --> E{EvidenceAgent}
  E -- rework / revisit --> D
  E -- accepted --> C[CodegenAgent] --> EV[EvalAgent] --> O[OptimiserAgent]
  O -- measurements --> M

Run-level budgets for ASE itself: 3 hours latency (a recorded decision dated 2026-09-21, because the optimiser alone is 96% of the path) and 1,000,000 tokens. The model also records ASE's own known gaps (TrustBoundaryGap, GateVisibilityGap, HierarchyGap, ExternalKindGap) as stated positions rather than hiding them.

models/ase-evolution.sysml holds the workbench at each increment, I0 to I6, as its own pattern, with @Release, @Delta (stub, introduce, extend, replace, measure) and @Realises (which IDEF0 activity each step performs). orchestrator.build() generates the running LangGraph from the current increment's flows.

How we work

Item by item, with a review gate

  1. Every item has a written goal, the files it touches, a definition of done, and its model delta if it changes ASE's agents, flows or tools.
  2. The model delta (ase-system.sysml, ase-evolution.sysml) lands before the code.
  3. One item per pull request, rebased on current main, small enough to review in one sitting.
  4. Verify (cli selftest plus tests), report, and wait for approval before the next item.

Three test layers

LayerWhat it checksWhere
L1 Gate and self-modelModels pass the structural gate; the sweep has no errors; the orchestrator regenerates identically; every step realises an activitycli selftest, tests/test_selfmodel.py
L2 Spec oraclesEach RS-xx end to end with the scripted stakeholder. What the current increment cannot meet is xfail naming the increment that will; burn them down, never delete assertionstests/specs/test_rs_xx.py
L3 Generated productThe generated agent on real data clears its metric thresholds; from I4 through its deployed endpointmarked slow

Tests run with no FalkorDB and no model calls. If your change needs a key or a database to pass its tests, it's not done.

Pull request checklist

  • Rebased on current main, no conflicts.
  • models/, methodology/ and skills unchanged, or the change is a reviewed library change and says so.
  • No provider SDK imported in pipeline, agent or codegen code.
  • A new step has an @Realises entry, and cli selftest is OK.
  • Offline tests pass with no key and no database.
  • Generated files regenerated, not edited.
  • Runs go through projects (workspace/<id>/runs/), not ad-hoc folders.

Your first week

Python environment: conda DATAENLIGHT_AI_ARCH_PATTERNS, with the root requirements.txt plus ASE Agentic System/requirements.txt. On Windows set PYTHONIOENCODING=utf-8. From ASE Agentic System/:

python -m sysmlagents.cli selftest                    # L1: should end with OK
python -m pytest tests -m "not slow" -c tests/pytest.ini
python -m sysmlagents.cli run docs/specs/RS-01-hr-policy-assistant.md --offline
python -m sysmlagents.cli trace RS-01                # the steps of that run
python -m sysmlagents.cli explain RS-01
python -m sysmlagents.cli up                         # Docker + FalkorDB + graphs + workbench app
  1. Day 1. Read CLAUDE.md, then this handbook, then docs/ROADMAP.md sections 2 and 3.
  2. Day 2. Run the commands above. Open the workbench and follow one RS-01 run step by step in the Step Inspector.
  3. Day 3. Read models/rag-patterns.sysml and the AseWorkbench part of models/ase-system.sysml. Compare one pattern's computed numbers with the table above.
  4. Day 4. Read RS-01 and RS-02 in docs/specs/, including the hidden oracle, and tests/specs/test_rs_01.py.
  5. Day 5. Pick a first item with your reviewer and write its one-paragraph item spec before any code.

Known documentation drift. A few documents disagree with the code; trust the code and models. ase-system.sysml, README.md and the roadmap say 36 checks; there are 34. Glossary

Control
Something an activity must obey and may not change: viewpoints, perspectives, pattern library, catalogue, stakeholder agreement.
Input
Something an activity consumes and may transform: the spec, scenarios, draft views.
Spec (RS-xx)
A reference specification with a submitted part and a hidden test oracle.
Project
One design in the workspace: spec/, inputs/, design/, runs/, journal.jsonl. Keys its graph partition.
Stage
One step of an agent's pipeline, with declared estimates (calls, latency, tokens, fan-out, provenance, fallback).
Pattern
A named composition of stages and flows, with requirements it satisfies.
@Extension
A recorded departure from the library, with a reason, on a design. Promoted into the library only by a human commit.
@Realises
Metadata linking an ASE step to the IDEF0 activity it performs.
Increment (I0 to I6)
One release of the workbench, modelled in ase-evolution.sysml.
Gate
The structural SysML check (check_model.py) that decides well-formedness before anything reads a model.
Sweep
Running all 34 perspective checks over a model.
Oracle
The expected outcome for a spec: pattern, questions asked and not asked, findings, decisions, metrics.
GEPA
Reflective prompt optimisation for DSPy programs; used with a held-out acceptance gate.
