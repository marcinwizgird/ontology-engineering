# Anchor SIP's ontology views in search

The state of the art in ontology visualization is less settled than tool demos suggest. The field has many notations (VOWL, Chowlk, OWLGrEd, Graffoo, Graphol) but only a thin evidence base. The single strongest controlled result is that **indented trees beat node-link graphs for finding things, while graphs help users process local relationships, and accuracy differences are mostly not significant**. That comes from one eye-tracking study of 36 novice students working on ontologies of 74 to 181 entities, far below FIBO's roughly 3,000 classes. Every system that copes with large graphs works the same way: search for a seed, extract a bounded neighbourhood on the server, render it, then expand on demand under a hard cap. None attempts a full node-link overview of FIBO. On the engineering side, open libraries are mature: Cytoscape.js is MIT-licensed, ships a no-build UMD file and supports compound nodes and layered layouts. The genuinely open gap is workflow integration. I found no maintained tool that overlays staged changes, validator findings, inferred-versus-asserted state or competency-question coverage onto an ontology diagram, and those are exactly the data SIP's `Platform.call` operations already return. My recommendation is a PoC in `LAB/PoCs` built around a search-first TBox ego view. It should vendor Cytoscape.js and add one missing operation (a TBox neighbourhood subgraph), make the review-gate diff overlay its headline feature, and measure itself against the existing `browse.classTree` as the baseline. LLM-generated diagrams, visual editing and whole-FIBO overviews should come later, behind evidence gates.

## Notations trade fidelity for readability, and none draws FIBO's class expressions completely

The notations fall into two families, and they differ mainly in how they handle class expressions, which matters because FIBO depends heavily on restrictions. **VOWL 2**, the final version of the VOWL spec, is a force-directed node-link notation that deliberately covers only the TBox. It handles classes, properties, domain/range, subclass, equivalence, disjointness, anonymous set operators and cardinalities. It has **no notation for named classes defined by set operators, for nesting order ("a union including an intersection and an intersection including a union look the same"), for custom data ranges, or for oneOf enumerations**, and its authors admit that large ontologies are "not yet sufficiently addressed" ([Lohmann et al., SWJ](https://www.semantic-web-journal.net/content/visualizing-ontologies-vowl-0)). Its random force layout also reshuffles nodes on every render, which "prevents users from creating a 'mental map'" ([VOWL SWJ](https://www.semantic-web-journal.net/content/visualizing-ontologies-vowl-0)). The UML-style family handles expressions better. **OWLGrEd** puts Manchester-syntax text inside class boxes, which is compact and complete but less visual ([CEUR Vol-596](https://ceur-ws.org/Vol-596/paper-05.pdf)). **Chowlk** writes restrictions as tags on property arrows, such as `(some)`, `(all)`, `(N1..N2)` and an `(eq)` prefix for equivalence, and uses operator circles for ∩/∪/≡/⊥ and hexagons for oneOf. Colour carries no meaning in Chowlk, unlike VOWL and Graffoo, which helps black-and-white printing and colour-blind readers ([Chowlk VOILA 2023](https://ceur-ws.org/Vol-3508/paper2.pdf)). **Graffoo** draws restrictions as extra boxes, and its spec has not changed since v1.0 in 2013 ([Graffoo spec](https://essepuntato.it/graffoo/specification/)).

The evidence for choosing between these notations is weak. Chowlk's comparison with WebVOWL and Graffoo was written by Chowlk's own authors, with no user evaluation, and the paper lists a "detailed comparison ... in terms of capabilities, clarity" as future work ([Chowlk VOILA 2023](https://ceur-ws.org/Vol-3508/paper2.pdf)). I found no user study comparing Chowlk, Graffoo and OWLGrEd. The practical reading for SIP is that a Chowlk-style edge-tag convention suits small conceptual diagrams, and Manchester text (which SIP already produces through `browse.classFrame`) is the only faithful fallback for deeply nested FIBO expressions. Note also that the VOWL spec domain now redirects to an unrelated site, so the spec links in older papers are dead ([vowl.visualdataweb.org](http://vowl.visualdataweb.org/v2/)).

The view types have uneven support. Surveys agree that **2D node-link diagrams of class hierarchies dominate tools, while visual variety and OWL 2 support stay low and supported tasks are often unclear** ([Dudáš et al., KER 2018](https://cambridge.org/core/journals/knowledge-engineering-review/article/ontology-visualization-methods-and-tools-a-survey-of-the-state-of-the-art/5EA8C64D7DF60A84F6D2B7B9A09B6E6A)). Space-filling views have one controlled ontology result. OntoPlot combines an icicle plot, compression of "uninteresting" subtrees in a linear-time pass, and association display, and in a domain-expert user study it beat Protégé on accuracy and task completion ([OntoPlot, arXiv 1908.00688](https://arxiv.org/pdf/1908.00688)). Matrix and cube views serve dense alignment comparison ([Alignment Cubes, ISWC 2017](https://iswc2017.ai.wu.ac.at/paper-304/)). SKOS tooling settled long ago on hierarchy browsers plus indexes: SKOS Play produces alphabetical, KWIC and alignment tables and D3 tree, icicle-like and sunburst-like views ([skos-play README](https://github.com/sparna-git/skos-play)). SHACL shapes are conventionally drawn as UML class diagrams through PlantUML ([SHACL Play Draw](https://shacl-play.sparna.fr/play/draw)), which needs Java and is therefore unavailable here. Diffs remain textual. ROBOT diff emits plain, pretty, Markdown and HTML Manchester output, with no graphics ([ROBOT diff](https://robot.obolibrary.org/diff)). Among documentation generators, only Widoco embeds an interactive diagram (WebVOWL, also Java-dependent), while pyLODE produces diagram-free static HTML ([Widoco](https://github.com/dgarijo/Widoco); [pyLODE](https://github.com/RDFLib/pyLODE)). The Protégé plugins are legacy. OntoGraf's repository was last pushed in 2018, and OWLViz needs native Graphviz ([GitHub ontograf](https://api.github.com/repos/protegeproject/ontograf)), so for SIP both are design references only: an asserted/inferred toggle and filterable relation types.

## The evidence favours trees for lookup and graphs for local reasoning, and proves little else

The empirical record is small, mostly about novices, and mostly about toy ontologies. **Fu, Noy and Storey** are the best study: 36 students, eye tracking, and mapping-validation tasks on OAEI and reduced BioMed ontologies of 74 to 181 entities. Indented lists produced fewer fixations, shorter scanpaths and faster tasks. Graphs produced shorter fixation durations, meaning faster processing of information once found. **Accuracy and workload were inconclusive** ([Fu et al., SWJ](https://www.semantic-web-journal.net/system/files/swj861_0.pdf)). Every participant spent more time searching than processing, which the authors take as a mandate for search support in any visualization. Qualitatively, participants found trees confusing under multiple inheritance (duplicated nodes) and graphs "time-consuming, distracting and frustrating" ([Fu et al.](https://www.semantic-web-journal.net/system/files/swj861_0.pdf)). Even this study is limited: all participants were novices, the ontologies were tiny, and it is a single study.

The rest of the evidence is weaker still. **VOWL's evaluation is qualitative and author-run**. A reviewer counted 6 and 5 participants in its first two studies ([SWJ review](https://semantic-web-journal.net/node/892)), and its expert arm was a think-aloud with five ontology users, three of whom found the display "almost too much" ([VOWL SWJ](https://www.semantic-web-journal.net/content/visualizing-ontologies-vowl-0)). **Chowlk shipped with no user evaluation**: "Because of the simplicity of the tool, we do not include user experience evaluation" ([ESWC 2022](https://2022.eswc-conferences.org/wp-content/uploads/2022/05/paper_90_Chavez-Feria_et_al.pdf)). I found no comprehension study of OWLGrEd. The only quantitative pooling is an **unpublished 2014 student report** that meta-analysed four Protégé-baseline studies (TGViz, KC-Viz, OWL-VisMod, Fu et al.; n of 21 to 36 each) and found a mean Cohen's d of 0.014 with a 95% CI of −1.21 to 1.22 ([Saghafi 2014, UBC](https://www.cs.ubc.ca/~tmm/courses/547-14/projects/arash/report.pdf)). That interval means "no evidence of a general advantage", not "no effect". The signs suggest a consistent trade-off: alternative views cost time or accuracy on lookup and gain on satisfaction. KC-Viz, which starts navigation from automatically extracted key concepts, was the one alternative with a clear time advantage (d = 1.01, n = 21), a second-hand figure worth noting because it supports search- and summary-first design ([Saghafi 2014](https://www.cs.ubc.ca/~tmm/courses/547-14/projects/arash/report.pdf)).

Two newer findings matter for SIP's audiences. Interviews with 19 KG practitioners found a "lack of efficacy" of node-link diagrams for KG *consumers*, who want domain-specific views. Builders, by contrast, want schema enforcers ([Li et al., TVCG 2023](https://arxiv.org/abs/2304.01311v3)). A qualitative study of LinkQ, an LLM-to-KG-query tool with visual explanations, found that **14 practitioners, experts included, over-trusted wrong LLM outputs because the visualizations looked helpful** ([LinkQ, arXiv 2505.21512](https://arxiv.org/abs/2505.21512)). That is a weak, single, uncontrolled preprint, but it is the only empirical signal on assisted exploration, and it points to a specific risk for an agent-assisted platform. **No study I found tested OWL visualization with human participants at 1,000 or more classes.** Every claim in this report about FIBO-scale usability is therefore an extrapolation from small ontologies or from generic graph research.

## Every scalable system starts from a seed and expands under a cap

At FIBO scale, the design question is less which picture to draw than how much of the graph to send. Van Ham and Perer's degree-of-interest (DOI) model is still the reference design. Users with "semi-specific information needs" search, see a context subgraph ranked by `DOI = α·API + β·UI + γ·D` (a priori interest, search-derived user interest, and distance from the focus), then expand on demand. A diffusion term is needed because a plain threshold on a graph leaves disconnected fragments. The model was demonstrated on a citation graph of **more than 300,000 nodes and 3.3 million edges** served to thin web clients ([van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)). The same pattern recurs elsewhere. Paged Graph Visualization incrementally explores "very large RDF ontologies" while keeping already-placed nodes still ([PGV](https://corescholar.libraries.wright.edu/knoesis/225)). Reactodia starts from an empty canvas, adds `owl:Class` entities found by lookup, and runs layout in a Web Worker ([Reactodia](https://github.com/Reactodia/reactodia-workspace)). Neo4j Bloom caps scenes at 100 to 10,000 nodes and streams and deduplicates results ([Neo4j blog](https://neo4j.com/blog/developer/fetching-large-amount-data-neo4j-reactive-driver-the-bloom-case/)), and Siren adds a "big nodes threshold" that asks the user before expanding a hub ([Siren docs](https://docs.siren.io/siren-platform-user-guide/14.8/graph-browser/t_config-graph-browser.html)). Whole-graph renderers fail sooner: the OntoPlot authors hit WebVOWL scalability problems at "hundreds or thousands of classes" ([OntoPlot](https://arxiv.org/pdf/1908.00688)).

The only rigorous rendering numbers come from one 2025 peer-reviewed benchmark: 481 graphs, one RTX 3060 machine, 1-pixel unlabeled marks. At an edge-to-node ratio of 1, the largest graphs still above **30 fps were about 2k nodes for D3-SVG, 5k for D3-Canvas and 7k for WebGL**. Above 10 fps the limits were 7k, 15k and 20k ([PMC12061801](https://pmc.ncbi.nlm.nih.gov/articles/PMC12061801/)). Those figures flatter real ontology views, because labels dominate cost and class names are long, and the study did not test Cytoscape.js or sigma.js. Cytoscape's own vendor figures show its Canvas renderer at about 20 fps for 1,200 nodes with 16,000 edges, against over 100 fps with its experimental WebGL renderer, and about 3 fps at 3,200 nodes with 68,000 edges ([Cytoscape blog](https://blog.js.cytoscape.org/2025/01/13/webgl-preview/)). Claims of 10^5 nodes at interactive rates for sigma.js and Cosmos are **vendor claims without published methodology** ([sigma docs](https://v4.sigmajs.org/concepts/rendering/); [cosmos](https://github.com/cosmograph-org/cosmos)). The practical budget is therefore SVG or Canvas for ego views of a few hundred labelled nodes, with WebGL reserved for ABox projections in the 10^4 range. Bloom's 10k cap marks a sensible ceiling for any single scene.

Layout cost points the same way. Taxonomies with multiple inheritance are DAGs, so layered (Sugiyama) layout fits them, but crossing minimization is **NP-hard even for two layers** ([KIT lecture](https://algo.iti.kit.edu/_media/teaching/winter2019/graphvis/graphvis-ws19-v11.pdf)). Layered layout should therefore be confined to bounded subgraphs. I found no benchmark for dagre or ELK at 1k to 10k nodes, so claims that dagre degrades in the low thousands are unverified folklore. For a whole-ontology overview, the principled options are precomputed: key-concept summaries such as KCE, which powered KC-Viz ([KMi KCE](https://kmi.open.ac.uk/technologies/name/kce)), or RDF Digest ([SWJ](https://content.iospress.com/articles/semantic-web/sw264)), and Holten's hierarchical edge bundling over a containment tree ([Holten 2006](https://research.tue.nl/nl/publications/hierarchical-edge-bundles-visualization-of-adjacency-relations-in/)). FIBO supplies that containment tree for free, running domain → sub-domain → module → ontology ([FIBO Viewer](https://spec.edmcouncil.org/fibo/ontology/SEC/Debt/Bonds/Bond)), and it marks each ontology as release, provisional or informative ([FIBO Primer](https://spec.edmcouncil.org/fibo/doc/FIBO_Primer.pdf)), a cheap default filter. One warning: **up to a third of FIBO changed at class level per quarter** in a 2021 analysis ([arXiv 2108.05401](https://arxiv.org/pdf/2108.05401)), so any precomputed layout must be regenerated each release and reconciled to keep users' mental maps intact. I found no study of layout stability across FIBO releases.

## Cytoscape.js fits a no-build Python stack, and most ontology-specific tools do not

The library landscape suits SIP's constraints. **Cytoscape.js** is MIT-licensed, at v3.34.4 (October 2026), with about 11M weekly downloads, a 436 KB UMD file and 134 KB gzipped. It has native compound nodes, selector-based filtering and styling, and layout extensions for dagre, ELK and fCoSE ([GitHub](https://github.com/cytoscape/cytoscape.js); [npm](https://www.npmjs.com/package/cytoscape)). Its WebGL renderer, experimental since 3.31, does not yet support every style ([Cytoscape blog](https://blog.js.cytoscape.org/2025/01/13/webgl-preview/)). **@dagrejs/dagre** 3.1.1 is MIT and 49 KB, and the legacy `dagre` and `dagre-d3` packages have been frozen since 2019 ([npm](https://www.npmjs.com/package/@dagrejs/dagre)). **elkjs** has the strongest open layered layout, but its bundle is 1.6 MB and it is **dual EPL-2.0/GPL-3.0, not MIT** ([npm elkjs](https://www.npmjs.com/package/elkjs)), so it needs a licence-inventory entry. vis-network (Apache-2.0 or MIT) is the quickest fallback, with a built-in hierarchical layout and an editing toolbar in a single 652 KB UMD file ([npm](https://www.npmjs.com/package/vis-network)). For large instance graphs, sigma.js v4 with graphology (MIT, WebGL) is the conventional choice ([npm sigma](https://www.npmjs.com/package/sigma)). If GPU layout is ever needed, only the MIT `@cosmos.gl/graph` qualifies, because **the Cosmograph packages are CC-BY-NC-4.0** ([npm @cosmograph/cosmos](https://www.npmjs.com/package/@cosmograph/cosmos)). React Flow, despite its quality, needs a React build ([npm](https://www.npmjs.com/package/@xyflow/react)), which conflicts with SIP's no-build workbench.

On the Python side, no wrapper is worth adopting. pyvis has been stale since 2023 and bundles vis 9.1.2, ipycytoscape is Jupyter-only with no PyPI release since 2022, and pygraphviz needs native Graphviz ([PyPI pyvis](https://pypi.org/project/pyvis/); [PyPI ipycytoscape](https://pypi.org/project/ipycytoscape/)). The clean route is rdflib → networkx (already a core dependency) → JSON from the standard library → vendored JS. `networkx.cytoscape_data()` emits Cytoscape JSON directly, although this note comes from background knowledge rather than a re-checked source ([networkx docs](https://networkx.org/documentation/stable/reference/readwrite/generated/networkx.readwrite.json_graph.cytoscape_data.html)). Mermaid is MIT and very active, but its minified bundle is 5.5 MB and it suits static snippets, not exploration ([npm mermaid](https://www.npmjs.com/package/mermaid)).

Most ontology-specific tools fail SIP's constraints. WebVOWL is MIT and still receives pushes, but its converter, OWL2VOWL, is Java on the OWL API, and no Python port exists ([OWL2VOWL](https://github.com/VisualDataWeb/OWL2VOWL)). An rdflib-to-VOWL-JSON emitter is feasible but would bring in a notation with known gaps. Ontodia is archived ([GitHub](https://github.com/metaphacts/ontodia)). Its maintained fork, **Reactodia** (LGPL-2.1+, v0.35.2, August 2026), is the best open explore-and-edit canvas, and the VisGraph editor built on it already distinguishes OWL-RL inferences from assertions ([npm](https://www.npmjs.com/package/@reactodia/workspace); [VisGraph](https://dataportal.material-digital.de/en/dataset/visgraph-interactive-rdf-ontology-canvas)). It requires React, TypeScript and LGPL-compliant separate loading, though. The **FalkorDB Browser is SSPL-licensed**, so it should run only as the separate admin tool it already is on :3000, while the new MIT `@falkordb/canvas` (v0.3.3) is a young but legitimate embedding candidate ([FalkorDB Browser LICENSE](https://github.com/FalkorDB/falkordb-browser/blob/staging/LICENSE.txt); [npm @falkordb/canvas](https://www.npmjs.com/package/@falkordb/canvas)). **Neo4j NVL "may only be used with" Neo4j products** and is ruled out ([NVL LICENSE](https://unpkg.com/@neo4j-nvl/base@2.0.0/LICENSE.txt)). The commercial tools (yFiles, quote-only; GoJS, from $3,995; Ogma) offer better layered layouts and folding, but their performance claims come from the vendors ([GoJS pricing](https://gojs.net/latest/pricing)). For UX, the closest functional reference is VocBench 3's graph view, since SIP ports VocBench. It has data-oriented, model-oriented and class-diagram perspectives, expand-from-node, language filters and SVG export ([VocBench docs](https://vocbench.uniroma2.it/doc/user/graphs.jsf)). The TopBraid EDG diagram, which shows class boxes listing properties with range and cardinality, is the reference for a class-diagram idiom ([TopQuadrant blog](https://topquadrant.com/blog/visual-exploration-of-ontologies-with-topbraid-edg)).

## Workflow overlays are the open gap that SIP's staged-commit model can fill

The 2022–2026 frontier is about putting diagrams inside engineering workflows rather than about new notations. Here the findings are absences as often as presences. **LLM assistance in shipping products is NL-to-query, not NL-to-view.** GraphDB's Talk to Your Graph, metaphactory 5.5's beta conversational interface, Stardog Voicebox and NeoDash Text2Cypher all generate SPARQL or Cypher and show answers in chat, tables or dashboards ([metaphactory 5.5](https://metaphactory.com/metaphactory-5-5); [NeoDash docs](https://www.neo4j.com/docs/neodash-commercial/current/user-guide/extensions/natural-language-queries)). I found no documented feature that turns a question into a curated ontology diagram or has an LLM explain a diagram. Stardog's "free of hallucination" claim is marketing ([Stardog](https://stardog.com/product)), and Neo4j's own Text2Cypher paper concedes that LLMs produce "incomplete or incorrect outputs" ([arXiv 2412.10064](https://arxiv.org/html/2412.10064v1)). When ChatGPT was asked for a Mermaid diagram of DBpedia's main classes, it returned a subClassOf tree using only two properties ([Meyer et al., arXiv 2307.06917](https://arxiv.org/pdf/2307.06917)), an anecdote rather than a study. By contrast, deterministic schema-diagram generation from OWL has been reported to outperform VOWL and OWLGrEd ([Shimizu et al.](https://corescholar.libraries.wright.edu/cse/748)). OntoChat, the leading research system, targets requirements and CQ elicitation and has no visual layer ([arXiv 2403.05921](https://arxiv.org/abs/2403.05921v1)). The defensible pattern is for the LLM to choose the subgraph and deterministic code to draw it.

**Visual editing is mature one way and rare round trip.** Chowlk converts diagrams.net XML to OWL, and its authors deliberately chose not to build an editor ([ESWC 2022](https://2022.eswc-conferences.org/wp-content/uploads/2022/05/paper_90_Chavez-Feria_et_al.pdf)). Eddy draws Graphol diagrams with design-time syntax validation and exports OWL 2, but the Graphol spec is CC BY-NC-ND ([IJCAI-16](https://cs.unibg.it/savo/papers/LPSS-IJCAI-16.pdf)). The WebVOWL Editor supports only a subset of OWL ([Fraunhofer](https://publica.fraunhofer.de/handle/publica/407769)), and metaphactory stores diagrams as artifacts that travel with the ontology ([metaphactory 5.5](https://metaphactory.com/metaphactory-5-5)). Every one of them keeps layout separate from the OWL, and none describes re-syncing a hand-tuned layout when the underlying model changes. For SIP, Chowlk's pipeline (diagram → converter → Turtle delta) maps naturally onto "agent proposes a staged commit".

**Reasoning visualization is a research topic.** Evonne offers coordinated proof and ontology views, colour-coded cross-highlighting and "what if" axiom removal, and was evaluated qualitatively with 16 logic experts ([Méndez et al., CGF 2023](https://diglib.eg.org:443/handle/10.1111/cgf14730)). It rests on DL justification algorithms ([Kalyanpur et al.](https://research.manchester.ac.uk/en/publications/finding-all-justifications-of-owl-dl-entailments/)) that SIP cannot run, because owlrl is OWL 2 RL and HermiT and Pellet need Java. The precedent that does transfer is the cheap one: Swoop marked unsatisfiable classes in red with plain-language explanations ([W3C list, 2005](https://lists.w3.org/Archives/Public/public-owl-dev/2005AprJun/0008.html)), and VisGraph styles inferred knowledge differently from asserted.

**Overlays of findings and change states are the clearest gap.** OOPS! returns pitfall lists with severities ([SWJ](https://www.semantic-web-journal.net/node/989)). SHACL validation produces RDF reports, and I found no visualizer for reports as opposed to shapes ([ShapeUML](https://w3id.org/imec/unshacled/spec/shape-uml/20210118)). VocBench presents accept/reject queues ([VocBench tips](https://vocbench.uniroma2.it/doc/tipsntricks)), and ROBOT and the ODK diff action produce textual axiom diffs on pull requests ([ODK v1.3.1](https://github.com/INCATools/ontology-development-kit/releases/tag/v1.3.1)). A systematic review of ontology *change* visualization found 28 tools, of which only 12 were still available ([SWJ 3622](https://www.semantic-web-journal.net/system/files/swj3622.pdf)). **No maintained tool I found paints these onto the diagram.** CQ coverage is in the same position. Coverage *measurement* is an active field, with CQGen-MAS defining coverage through the ontology terms each CQ's SPARQL references ([AAMAS 2026](https://ifaamas.org/Proceedings/aamas2026/pdfs/RRYE6579.pdf)), but no tool *visualizes* which classes the CQs exercise. CQ metrics are also not comparable across papers ([CEUR Vol-3953](https://ceur-ws.org/Vol-3953/369.pdf)). For mappings, user studies favoured the graph-based RMLEditor/MapVOWL over form-based editing ([Heyvaert et al., JWS 2018](https://ruben.verborgh.org/publications/heyvaert_jws_2018/)), although recent tools such as Matey are text IDEs with linked panels ([CEUR Vol-3999](https://ceur-ws.org/Vol-3999/paper3.pdf)). Because "absence of evidence" findings depend on search coverage, treat these gaps as strong hypotheses rather than certainties. VOILA 2022–2025 was not searched systematically.

## Evaluate with Munzner's nested model, not with preference scores

The methodology literature supplies a frame but no standard instrument. Munzner's nested model separates domain, abstraction, idiom and algorithm, and gives each a threat ("wrong problem", "wrong abstraction", "wrong idiom", "too slow") and a validation method: system time and memory at the algorithm level, lab studies of human time and errors at the idiom level, and observation of target users at the domain level. Errors upstream invalidate everything downstream ([Munzner 2009](https://www.cs.ubc.ca/labs/imager/tr/2009/NestedModel/)). Task batteries can draw on Lee et al.'s graph task taxonomy of topology, attribute, browsing and overview tasks ([Lee et al., BELIV 2006](https://www.microsoft.com/en-us/research/publication/task-taxonomy-graph-visualization/)). Prior ontology studies used completion time, accuracy and custom questionnaires. I saw no SUS or NASA-TLX reports and no error-detection tasks, the latter being a gap directly relevant to a validate stage. In every meta-analysed study the de facto baseline was Protégé's indented list ([Saghafi 2014](https://www.cs.ubc.ca/~tmm/courses/547-14/projects/arash/report.pdf)).

There is also no standard rendering benchmark. Published numbers come from vendors or authors, on single machines with differing graphs. Cytoscape's library comparison shows why "time to first frame" and "time to stable layout" must be reported separately: sigma's force layout never halts on its own ([js-graph-lib-comparison](https://github.com/cytoscape/js-graph-lib-comparison/blob/master/README.md)). NetV.js's claim of beating every competitor at 50k nodes is self-reported ([DOAJ](https://doaj.org/article/a199b80883cc47a1b6b53ac02ad185a2)). A PoC must therefore define its own protocol on its own data. For assisted exploration, the LinkQ over-trust finding means that preference and accuracy are not enough. An evaluation must measure **trust calibration**: how often users accept wrong agent answers and reject correct ones, with seeded errors as the probe ([LinkQ](https://arxiv.org/abs/2505.21512)). Power is a constraint. A within-subject paired test needs roughly 34 participants for d ≈ 0.5 at 80% power (standard arithmetic, not from the sources), so a PoC study with a handful of users must be declared **formative** from the outset.

## Conclusion

The research changes the framing of the task. Ontology visualization is usually treated as a rendering problem (which library, which notation, how many nodes), but the evidence says rendering is the solved part and the unsolved parts are query and workflow. Users spend most of their time searching. Large graphs are tolerable only as bounded neighbourhoods. The features no maintained tool offers (diff, findings, inference and CQ-coverage overlays, all keyed by IRI) are precisely the ones SIP's architecture makes nearly free, because staged commits, validators, owlrl and executable CQs already emit IRI-addressed data. SIP's distinctive contribution is therefore not a better diagram but **a diagram that is a view over the review gate**.

The thinness of the evidence is also an opportunity. No published study tests ontology visualization at FIBO scale, uses error detection as a task, or measures trust in agent-assisted views. A PoC that logs these properly would produce evidence the field lacks, provided it is honest about being formative and treats the existing `browse.classTree` as a strong baseline to beat rather than a strawman.

## Recommendations for SIP

### PoC scope: one search-first ego view with review-gate overlays

Create `LAB/PoCs/ontology-visualization/` following the PoC conventions: `README.md`, `PLAN.md`, `RESULTS.md`, a Python package (say `ontoviz/`), offline `tests/` and `artifacts/`. The PoC should answer one question: **can a bounded, overlay-rich TBox ego view built on existing `Platform.call` operations help a reviewer at the review gate more than the class tree and pending-commit list alone, at FIBO scale, within the Canvas budget?**

The backend should be pure Python over rdflib and networkx, with no new dependency. Its core is a prototype of the one missing operation, a **TBox neighbourhood** function `(seed IRI, hops, edge kinds, N cap) → {nodes, edges}`. It should follow subClassOf, equivalence, property domain/range and restriction edges, rank candidates with a simplified van Ham–Perer DOI (hop distance plus edge-kind weights plus a degree-based a priori score), and apply a big-node guard that returns a "sample or confirm" marker instead of expanding hubs. Following Chowlk, restrictions should render as **tagged edges** (`hasParty (some)`, `(1..1)`) rather than blank-node vertices. Anything more nested than a single restriction should collapse to a node badge whose detail comes from `browse.classFrame`'s Manchester rendering. That is the OWLGrEd lesson, and it avoids drawing FIBO's anonymous-class explosion. A small companion should list individuals per class, prototyping the second gap, so ABox views do not depend on SPARQL alone. The output contract should be a **superset of the Ontology-Playground JSON** (`entityTypes[{id,name,kind}]`, `relationships[{from,to,kind,cardinality}]`). It should add `state` (asserted / inferred / staged_add / staged_del / imported), `findings[]` (check, severity) and `cq[]` (passing and failing CQ ids), and convert to Cytoscape elements in a few lines. Reusing that contract and its Cytoscape style rules in `frontend/INTEGRATION.md` avoids a third graph schema in the repo.

The overlays come straight from existing operations. Staged state comes from `browse.resourceView` scopes (local, staged, del_staged, imported, inferred) and `validation.pending` [s,p,o] additions and removals, with green for additions and struck-through red for removals. Inference comes from `reasoning.classify`: dashed for inferred triples, red outline for unsatisfiable classes, and its staged preview gives a before-and-after inference diff of a pending commit, which no surveyed tool offers. Findings badges come from `quality.runChecks` severities. CQ coverage comes from parsing the IRIs in each CQ's SPARQL, following the CQGen-MAS idea of "referenced terms", and colouring nodes by the number of passing and failing CQs that touch them. Clicking a node should call `browse.classFrame`, `browse.usage` and `history.list` in a side panel, giving coordinated views across *workflow artifacts* rather than across encodings.

The frontend should be a single static HTML page with **vendored** Cytoscape.js, `@dagrejs/dagre` and `cytoscape-dagre` (all MIT, roughly 500 KB in total), with fCoSE optional for compound module grouping. ELK, WebGL renderers, Mermaid and Reactodia are deliberately excluded from the PoC. dagre lays out the subClassOf spine and the remaining edges route on top. Seed a deterministic layout and keep placed nodes fixed on expand (the PGV principle) to protect mental maps. A SKOS mode should drive the same component from `skos.topConcepts` and `skos.narrowerConcepts` with broader/narrower as the spine. For static artifacts (PR comments, `RESULTS.md`, release notes), reuse the layered SVG generator in `capabilities/architecture/graphrag_agent/sysml_diagrams.py` rather than Mermaid or Graphviz. It needs no cairo, and SVGs can be verified structurally, as CLAUDE.md requires.

Explicitly out of scope for the PoC are whole-FIBO node-link overviews, visual editing, LLM-generated views, ABox rendering beyond a small capped `kg.projectLPG` sample, and VOWL-JSON emission. Offline pytest should cover cap enforcement, DOI ordering, restriction-edge tagging on FIBO fixtures, state tagging against a constructed staged commit, CQ-IRI extraction, and layout determinism (same input, same coordinates for the static SVG path).

### Evaluation plan

At the **algorithm level**, an automated benchmark should run as part of the PoC tests where possible and as a scripted browser run (for example Playwright) otherwise. It should cover FIBO ego graphs at N = 50, 100, 300 and 1,000, a full FIBO module, and synthetic graphs up to 10k nodes with ontology-like edge density. It should measure server extraction time (rdflib in-process versus Fuseki 5.1.0 CONSTRUCT, reported separately, since no published SPARQL latency figure for k-hop extraction on FIBO exists), data-to-first-paint, layout time, median and p5 fps during a scripted pan and zoom, expand and search-highlight latency at p50 and p95, and peak JS heap. Declare the thresholds in `PLAN.md` before measuring, for example ≥30 fps and <100 ms interaction latency at N ≤ 300 with labels on. These are conventional HCI targets, not evidence-derived. Use at least five measured runs after a warm-up and report medians and IQRs.

At the **idiom level**, run a formative within-subject study comparing three conditions: `browse.classTree` with search plus the textual pending list (baseline), the ego view without overlays, and the ego view with overlays. Counterbalance the order and use isomorphic tasks on a small ontology (about 100 to 200 classes, comparable to Fu et al.) and a FIBO module. Stratify 12 to 16 tasks across lookup, relationship (domain/range, path, multiple inheritance), overview, **seeded-defect detection** and **staged-commit review** (accept or reject a planted bad commit). The last two task types are SIP-specific and fill a gap in the literature. Accuracy is the primary measure, with time on correct trials, SUS and raw NASA-TLX as secondary measures. With 8 to 12 participants, which is realistic, report descriptives, effect sizes with CIs and qualitative themes, and no p-values.

At the **domain level**, run think-aloud sessions with a few ontology engineers and a few finance SMEs on realistic review-gate scenarios, coded thematically. This tests Li et al.'s warning that node-link diagrams fail consumers. Before Phase 4, an **assisted level** study should include seeded wrong agent answers and measure acceptance of wrong answers, rejection of correct ones and in-view verification, scored automatically against SPARQL ground truth on the canonical graph. Live-model runs are billed, so they need explicit user approval under the repo rules. The offline simulators can drive the protocol dry run.

### Risks

The largest risk is **building on weak evidence**. Apart from Fu et al.'s tree-versus-graph result and OntoPlot's single study, the design guidance here (DOI ranking, overlays, coverage colouring, Chowlk tags) is inference from small or adjacent studies. The mitigation is to keep the class tree as the default navigator and make the graph prove its value against it. **Scale risk** is concrete. Canvas Cytoscape degrades in the low thousands of labelled elements, and FIBO's roughly 3,000 classes plus restrictions exceed any single scene. Hard caps, the big-node guard and server-side extraction are requirements, not optimizations. **FIBO's expression complexity** may defeat the edge-tag convention. Nested restrictions, unions and property chains will appear as badges with Manchester text, so the view will look less complete than WebVOWL demos. That is the honest trade-off, and it should be documented.

**Reasoning limits** follow from owlrl. OWL 2 RL produces no DL justifications, so "why is this inferred or unsatisfiable" can show only what `reasoning.explain` already provides. Rule-firing provenance from owlrl is my inference, unverified, and may require instrumentation. The UI must not imply Evonne-grade explanations. **Licence risk** is manageable but real: elkjs is EPL/GPL, Reactodia is LGPL with a React build, the FalkorDB Browser is SSPL, the Cosmograph packages are non-commercial, and NVL is Neo4j-only. The PoC's all-MIT stack avoids all of them, and any later addition needs an entry in a vendored-asset licence inventory. **Vendored JS goes stale** without a Node toolchain to warn about updates, so pin versions and checksums and record them in the README. **Layout instability** across FIBO's high quarterly churn will erase users' mental maps unless layouts are stored as IRI-keyed artifacts and reconciled. **Over-trust** is likely to become the dominant risk once agents generate views. A polished graph makes a wrong agent claim more persuasive, which is why Phase 4 is gated on a trust-calibration study and every agent-generated view should carry its query and provenance. Finally, **scope creep** into visual editing is the classic failure mode of ontology-visualization projects. Every surveyed editor either supports only a subset of OWL or stops at one-way generation. SIP's staged-commit discipline is the guardrail: a diagram may *propose*, and only the validator and a human may accept.
