How we will know whether ontologies make bank-data questions safer

The proof of concept lets people ask questions about banking data in plain English. The evaluation answers two questions: does putting a business ontology (FIBO) between the question and the database give fewer wrong answers, and which part of it earns its keep?

27 October 2026Benchmark: IBM FIBEN, 152 tables, 11.7M rowsCompanion: technical specification
Measurement foundation: ready

The test bench is sound and its first gate passes. Every database instance, data shape and ontology check that guards the measurements is clean.

It found and fixed a defect in our own test data. One of the test databases had rows that broke its own key rules, which can make a correct query look wrong. We repaired it and re-ran every check. The published results moved by at most 5 points, and no conclusion changed.

What we know so far is limited but real. In the first small trial, the ontology approach gave significantly fewer confident wrong answers than plain text-to-SQL. No approach was clearly more accurate, and the sample is too small to detect differences under about 19 points.

New: the component check (Gate 2) is done, and it locates the weak step. The system finds the right business terms for only about a quarter of questions, and its current refusal rule turns away 23% of answerable questions. The knowledge written after seeing the benchmark answers inflated term finding by 25 points over knowledge drawn from training questions only.

Next: rebuild the runtime into swappable parts (free), then a ~US$10 diagnostic run.

How we measure

A ladder of six approaches, each adding one thing

If the ontology wins, we need to know why. Each step up the ladder adds exactly one capability, so each difference has one explanation.

L0

The database schema only

The AI writes SQL from table and column names. The baseline.

L1

Plus a written data dictionary

The same definitions the ontology holds, as plain documentation. Shows how much is gained by writing meaning down at all.

L1.5

Plus pre-built category views

"All financial figures" as one view instead of eight tables. Shows the value of the ontology's categories alone.

L2

The ontology, with query checks

The AI asks in business terms, the system translates to SQL and rejects invalid combinations.

L3

Plus knowledge of what the data holds, and a refusal gate

The system knows which categories are empty and refuses questions the data cannot answer, with an explanation.

L4

Plus several attempts and a self-check

Generates alternatives and checks the results before answering. The upper bound.

Why the results will be trustworthy

Five safeguards

  • The headline is safety. The main measure is the rate of confident wrong answers, which is the real business risk. A refusal is never counted as a success.
  • The test databases catch lucky answers. Every answer is checked on the real data and on six deliberately altered copies. An answer that is right only by coincidence fails.
  • The statistics are fixed in advance. The main hypothesis, the tests and the corrections are written down before the final test, so the results can't be shopped for. Re-worded versions of one question count once, not several times.
  • Benchmark leakage is controlled. Hand-written knowledge may use training questions only. The transfer test on a second bank dataset is set up before anyone reads its questions. A version with disguised table names checks that the AI isn't relying on memory of the public benchmark.
  • Every run is reproducible. Model version, prompts, knowledge and data are fingerprinted for every result.

What not to conclude yet. The first trial shows the ontology approach is safer, not that it is more accurate. Its accuracy is far below a product bar, and the trial was too small to tell the approaches apart on accuracy. The framework exists to settle this with enough questions and fair comparisons.
