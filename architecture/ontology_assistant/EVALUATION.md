# Evaluation

How to tell whether the Ontology Assistant Agent is actually working. Written before the
implementation on purpose: the metrics constrain the design.

Following the project convention, the harness is a set of **Jupyter notebooks executed
headless** (`jupyter nbconvert --execute`) acting as functional tests, generated by a
`_build_*.py` script, plus plain unit tests for the deterministic parts.

---

## 1. The competency-question gold set

Competency questions are the natural evaluation instrument for an ontology assistant — they
are already the ontology-engineering discipline's own acceptance criterion (Keet, Ch. 5–6),
and they double as F5 output.

**Structure:** 15–25 CQs per major module in scope, each with:

```yaml
- id: CQ-FBC-007
  question: "Which kinds of institution can provide a deposit account?"
  intent: discovery
  expected_anchors:
    - fibo-fbc-fct-fse:DepositoryInstitution
    - fibo-fbc-pas-caa:DepositAccount
  expected_citations:          # triples that MUST appear in the evidence bundle
    - [DepositoryInstitution, subClassOf, "restriction(provides some DepositAccount)"]
  must_not_claim:              # known distractors / false friends
    - "InvestmentBank provides DepositAccount"
  answerable: true
```

Include a deliberate **unanswerable** slice (~20% of the set): questions about domains the
loaded ontologies genuinely do not cover. These test abstention, which is otherwise
unmeasurable.

Store the gold set as YAML under `architecture/ontology_assistant/eval/` and load it into the
`assistant:` named graph so the CQ library is itself queryable.

## 2. Retrieval metrics

Measured on the Evidence Bundle, independent of the prose. This is the layer that actually
determines answer quality, and it is cheap to measure.

| Metric | Definition | Target |
|---|---|---|
| **Anchor recall@k** | fraction of `expected_anchors` present in the top-k anchors | ≥ 0.90 @ k=10 |
| **Anchor precision@3** | fraction of top-3 anchors that are relevant | ≥ 0.70 |
| **Evidence recall** | fraction of `expected_citations` present in the bundle | ≥ 0.85 |
| **Evidence precision** | fraction of bundle triples a human judges relevant | ≥ 0.60 |
| **Path validity** | fraction of returned paths where every hop verifies in Fuseki | 1.00 |
| **Budget efficiency** | tier-1–3 triples as a share of total bundle tokens | ≥ 0.70 |

**Anchor recall is the leading indicator.** If the right IRI never enters the funnel at stage
2, no amount of prompt work downstream recovers it. Track it per anchoring method (exact /
vector / structural) so the value of the embedder upgrade is directly visible — this is the
measurement that will justify or refute
[gap 1](STORE_PREREQUISITES.md#1-the-default-embedder-is-not-semantic).

## 3. Faithfulness metrics

| Metric | Definition | Target |
|---|---|---|
| **Hallucinated IRI rate** | IRIs in the answer that do not resolve in Fuseki | **0.00 — hard gate** |
| **Citation coverage** | factual sentences carrying ≥1 triple citation | ≥ 0.98 |
| **Citation validity** | cited triples that actually support their sentence (LLM-judged, human-audited sample) | ≥ 0.95 |
| **Falkor-only claim rate** | claims traceable only to the projection | 0.00 — hard gate |
| **Asserted/inferred conflation** | inferred statements presented as asserted | 0.00 — hard gate |

The three hard gates are all **mechanically checkable**, which is the point of the artifact
design: because the answer references triple ids from a bundle whose provenance is recorded,
verification does not require a judge model. The Grounding Critic runs these same checks
inline; the eval harness runs them in batch to catch regressions.

---

## 4. Abstention and honesty

| Metric | Definition | Target |
|---|---|---|
| **Abstention accuracy** | correct abstentions ÷ unanswerable CQs | ≥ 0.90 |
| **False abstention** | answerable CQs the agent declined | ≤ 0.05 |
| **Coverage statement accuracy** | stated coverage matches computed coverage | ≥ 0.95 |
| **Gap-report usefulness** | human 1–5 rating on gap answers | ≥ 4.0 |

An assistant that never abstains is confidently wrong at a rate nobody is measuring. This
block is what keeps the system trustworthy to a governance audience.

---

## 5. Comprehension quality (F1/F5, human-judged)

Digest and utilization output resists automatic scoring. Use a small rubric, 1–5, on a sample
of 20 module digests, rated by someone who is not an ontologist:

1. **Clarity** — understandable without RDF knowledge.
2. **Accuracy** — no statement contradicted by the module.
3. **Usefulness** — a reader could decide whether this module is relevant to their problem.
4. **Query readiness** — the example queries run and return sensible results (this one *is*
   automatable: execute every generated query and assert non-error, non-empty).

---

## 6. Performance

Assert against the budget in
[RETRIEVAL_PIPELINE.md §4](RETRIEVAL_PIPELINE.md#4-latency-budget): p50 and p95 per stage,
total turn under 5 s, cached follow-ups under 2 s. Run against the local
`infra/fuseki` + `infra/falkordb` stacks with the full ~133k-triple dataset — not a fixture —
because hydration cost is the stage that scales with real data.

## 7. Harness layout

```
architecture/ontology_assistant/eval/
  cq_gold/                 YAML gold sets, one file per module
  fixtures/                two-module FIBO subset for offline unit tests
  notebooks/
    01_retrieval_metrics.ipynb      anchor/evidence recall & precision
    02_faithfulness.ipynb           hard gates + citation validity
    03_abstention.ipynb             answerable vs unanswerable slices
    04_digest_quality.ipynb         query-executability + rubric capture
    05_performance.ipynb            latency percentiles
  _build_notebooks.py      generates the above, per project convention
  report.py                writes a single markdown scorecard
```

Two tiers of run:

- **Offline / CI** — fixtures only, no live stores, deterministic embedder, exercises
  ranking, verbalisation, critic logic, and schema contracts.
- **Live** — against the running stacks, full gold set, produces the scorecard.

---

## 8. Regression policy

The hard gates in §3 fail the build. Retrieval metrics are tracked over time with a tolerance
band; a >5-point drop in anchor recall blocks a projection change from being promoted. Every
projection change ([STORE_PREREQUISITES.md](STORE_PREREQUISITES.md)) must be accompanied by a
before/after scorecard — that is how the value of each gap fix gets demonstrated rather than
asserted.
