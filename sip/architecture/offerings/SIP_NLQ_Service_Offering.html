Semantic Intelligence Platform · Service offering · Draft for architecture review

Ontology services for natural-language query

The natural-language query (NLQ) team builds the experience. The Semantic Intelligence Platform (SIP) supplies the parts a language model cannot guarantee on its own: what the business terms mean, which data can answer a question, whether a query is valid, the exact SQL it compiles to, and evidence that the answer is right.

Audience: IT executives, IT managers, enterprise and solution architects · Basis: SIP design and a measured proof of concept on a public banking benchmark (October 2026) · Status: proposal, not a commitment

1 · Executive summary

Translating a question into SQL is easy to demo and hard to trust. On real enterprise schemas, language models produce queries that run and return plausible numbers but are wrong, with nothing to warn the user. The remedy the evidence supports is not a cleverer prompt. It is curated business meaning, deterministic query construction and checks, all of which SIP already owns.

Understand

SIP maps the user's words to governed business concepts, values and data paths, and says when a question falls outside what the data covers.

Guarantee

The language model never writes SQL. It proposes a plan in SIP's vocabulary. SIP checks the plan against the ontology and compiles it into exact SQL for the target database.

4 · How one question is answered

Example: "What price did Luis Statz sell DFRG at?" Each step names its owner. Steps 3–5 repeat at most twice when SIP's checks reject a plan. If the question can't be answered, the user gets a reason, not a guess.

5 · Service catalogue

Ten services in three groups. The status reflects the proof of concept, not a production SLA: proven in PoC  prototype, needs hardening  designed, not built

A · Knowledge services (design time · SIP curates · the NLQ team reads)

1

Business vocabulary

The governed meaning of business words: synonyms ("stock" = listed security), metric definitions ("revenue" = which figure, at which grain), code meanings (transaction type "2" = sale).

In: term or search text · Out: definitions, synonyms, linked concepts, version
proven: the glossary raised grounding recall from 48% to 64%
2

Semantic mapping and coverage

Mappings from ontology concepts to tables and columns (W3C R2RML), plus a coverage report: what the data can answer today, and what the ontology knows but the data doesn't map.

In: concept or area · Out: mapped / unmapped, source tables, owner
proven: 152 tables mapped automatically, reviewed alignment to FIBO
3

Value index

Looks up names, tickers, codes and places in the data, so "Alphabet" resolves to the exact stored value. Personal data is included only where policy allows.

In: phrase · Out: matching values with concept, attribute, confidence
proven: 81,681 values indexed
4

Grounding

Turns the words of a question into candidate concepts, values and the paths that connect them, using graph algorithms over the ontology. It flags when the concepts don't connect in the data.

In: question (+ phrases from the LLM) · Out: ranked candidates, paths, "not covered" hints
prototype: works; ranking needs tuning on customer questions

B · Runtime services (per question · deterministic · the NLQ product calls these)

5

Context pack

A compact, prompt-ready description of only the relevant part of the ontology (terms, links, attributes, matching glossary entries) for the NLQ team's language model.

In: grounding result · Out: structured context (JSON) + rendered text, size-bounded
prototype: content choices are being measured (see §7)
6

Plan validation

Checks the LLM's query plan against the ontology: unknown terms, wrong relationship direction, impossible combinations, accidental cross-joins. It returns precise repair messages the LLM can act on.

In: plan (JSON) · Out: pass, or a list of problems in plain language
proven: zero false alarms on 226 verified queries
7

Query compilation

Turns a validated plan into exact SQL for the target database (PostgreSQL, Snowflake, BigQuery, DuckDB). Joins, class hierarchies and dialect details are handled by the platform, never improvised by a model.

In: plan · Out: SPARQL + SQL + tables used; same input → same output
proven: offline compiler, 4–6 ms; 92% of benchmark queries expressible
8

Governed execution and explanation

Runs the compiled SQL read-only under the user's own database role, with hard timeouts and row limits. It returns rows plus lineage: concepts, path, SQL, glossary and mapping versions.

In: compiled query + user identity · Out: rows, lineage, audit record
prototype: timeouts proven; row-level security integration to build

C · Assurance services (release time and continuous · SIP referees)

9

Evaluation and release gate

Scores any NLQ build against gold questions on several test databases, built so that wrong queries can't pass by coincidence. It reports accuracy, confidently-wrong rate, refusals, cost and latency, and blocks releases below agreed thresholds.

In: NLQ build endpoint · Out: scorecard, regressions, go / no-go
proven: harness, test databases and paired statistics in place
10

Feedback and coverage backlog

Refusals, corrections and thumbs-down become work items: a missing mapping, a missing synonym, a new gold question. Each fix flows through SIP's review gate and the next release gate.

In: question, outcome, user feedback · Out: triaged backlog item, new gold case
designed: uses SIP's existing staged-change workflow

6 · The contract between the teams

One rule makes the split work: the language model writes a plan in SIP's vocabulary, never SQL. The plan is small, typed JSON. It can be validated, explained and compiled deterministically. Here is an example for "What price did Luis Statz sell DFRG at?"

What the NLQ team's LLM produces

{
  "nodes": [ {"id":"t","cls":"SecuritiesTransaction"},
             {"id":"a","cls":"FinancialServiceAccount"},
             {"id":"p","cls":"Person"},
             {"id":"s","cls":"ListedSecurity"},
             {"id":"m","cls":"MonetaryAmount"} ],
  "links": [ {"subj":"t","prop":"isFacilitatedBy","obj":"a"},
             {"subj":"a","prop":"isOwnedBy","obj":"p"},
             {"subj":"t","prop":"refersTo","obj":"s"},
             {"subj":"t","prop":"hasPrice","obj":"m"} ],
  "filters": [ {"target":"lastName","op":"=","value":"Statz"},
               {"target":"ticker","op":"=","value":"DFRG"},
               {"target":"type","op":"=","value":"2"} ],
  "projections": [ {"target":"amount"} ]
}

What SIP returns

validate → { "ok": true }
           or { "ok": false, "problems": [
             "Person isOwnedBy FinancialServiceAccount is the
              reverse direction; isOwnedBy goes from the
              account to the person" ] }

compile  → { "sql": "SELECT ... FROM FIBEN.SECURITIESTRANSACTION
              v1 JOIN ... WHERE v1.HASTYPE = '2' ...",
             "dialect": "postgres", "tables": [...] }

explain  → { "concepts": ["trade","account owner","stock"],
             "path": "trade → account → owner; trade → stock",
             "glossary": ["sold = transaction type 2"],
             "versions": {"ontology":"1.4","mapping":"2026-10-19"} }

7 · What the evidence says

A proof of concept on the public FIBEN banking benchmark: 152 tables and 11.7 million rows, aligned to the FIBO financial ontology. Five approaches were run with the same language model (Claude Sonnet 5.5) on 63 held-out development questions. An answer counts as correct only if it is right on the real data and on five test databases built so that wrong queries can't match by coincidence.

Context from published research (vendor-run, small benchmarks; read with care)
  • On an insurance benchmark, GPT-4 answered 16% correctly from raw SQL and 54% over a knowledge graph. Adding ontology checks and repair reached 72%, with 8% honest "I don't know" (Sequeda et al. 2023; Allemang & Sequeda 2024).
  • A 2026 study that lets the language model only choose among governed options, and builds the SQL in code, reports 97% vs 55% for direct generation, with zero confidently-wrong answers (semantic path compilation). That is the same design principle as SIP's plan contract.
  • dbt Labs (2026): a governed semantic layer reached 98–100% on modelled questions, but 0% on multi-hop questions outside its model. Multi-hop questions are where an ontology's relationships help.

8 · Operating model and governance

Answers get better through governed change, never through silent edits to prompts or mappings. Every improvement follows the same loop, and every step leaves an audit trail.

Mappings are the main ongoing cost, and the main lever for coverage. Every refusal of the form "this concept isn't mapped" is a backlog item with a business owner. Coverage grows where users actually ask.
The NLQ team can change prompts and models freely, because every release is scored by service 9 against the same gold questions. A regression is caught before users see it.
Any self-optimisation of prompts is a governed release, not online learning. An optimiser such as GEPA may propose improved prompts. Nothing ships without the scorecard and a human sign-off.

9 · Roadmap

Start with the deterministic services that carry the least risk and give the NLQ team an immediate safety net. Add grounding and context once real customer questions exist to tune them on.

Durations are indicative and assume one SIP engineer plus a part-time domain curator; they will be re-planned after Phase 1. The NLQ team builds its UI and LLM planner in parallel against the Phase 1 APIs.

Decisions needed from leadership

1 · Adopt the contract

The NLQ product sends query plans in SIP's vocabulary to SIP for checking and compilation, and does not generate SQL directly against production.

2 · Fund curation

A part-time domain curator per business area, for vocabulary and mapping review. The evidence says this is the highest-value investment.

3 · Agree the release gate

Thresholds for the confidently-wrong rate, correct-answer rate and refusals that a release must meet before users see it, set from the Phase 1 baseline.
