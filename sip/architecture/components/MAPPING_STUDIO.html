Mapping Studio and the Mapping Authoring Agent

An R2RML editor where people state what tables and columns mean, and an agent that drafts those statements for review. SIP compiles the R2RML. Nobody has to write Turtle.

Summary

R2RML is the contract between a bank's databases and its ontology. Today it is written by hand in Turtle. That needs someone who knows the schema, the ontology and R2RML's details at once, and who can keep one IRI policy consistent across hundreds of maps. Very few people know all three. The design removes the need to.

  • Mapping Studio is a workbench editor. People work with correspondences and with mapping patterns such as subclass table, discriminator column, join table and code table. Every edit is previewed on real rows and checked immediately.
  • The Mapping Authoring Agent drafts the mapping. It profiles the database, takes candidates from the deterministic mapping.suggest, and asks the model only where candidates are ambiguous. It compiles the maps, runs the editor's checks, and submits one staged proposal per triples map, with evidence.
R2RML stays the single source of truth

The Studio is a projection of the mappings graph. Every edit is an ordinary mapping.* change set with history, undo and staging. There is no editor-only format to drift.

Author with patterns, not triples

Twelve patterns cover what the SPARQL-2-SQL and FIBEN mappings needed. Each has a detector, a form, a compiler and its own checks.

Model proposes, critics decide, a person accepts

The agent can only stage. Ontology gaps it finds go to the ontologist as separate proposals.

Users and use cases

Personas

  • Data engineer knows schema, data and SQL; needs to say what tables mean without learning OWL or R2RML.
  • Ontologist / mapper decides correspondences and the IRI policy, reviews drafts, watches coverage.
  • Reviewer / steward accepts or rejects staged maps, with evidence and a sample of their output.
  • NL2Q engineer states the questions the mapping must answer, as tests.

Use cases

  1. Connect a database and see what is in it.
  2. Bootstrap a whole schema with the agent, then review.
  3. Map one table by hand with a pattern wizard and live preview.
  4. Define the IRI policy once for every map.
  5. Fix findings with one-click quick fixes.
  6. Write and run mapping tests.
  7. Repair after a schema change or ontology refactoring.
  8. Import an existing Ontop R2RML file and keep editing it.
  9. Export R2RML for Ontop, or the YAML spec for git review.

The IRI policy is an object

Every subject map and referencing object map is compiled from an EntityDef. Changing a base IRI or a key is one edit that recompiles every affected map in one commit.

<urn:sip:p:bank:r2rml#entity/customer>
    a sip:EntityDef ;
    sip:pathSegment "customer" ;
    sip:rootTable   "PUBLIC.CUSTOMER" ;
    sip:keyColumn   "CUST_ID" ;
    sip:sharedBy    "PUBLIC.RETAIL_CUSTOMER",
                    "PUBLIC.CORPORATE_CUSTOMER" .

Lifting R2RML into patterns

On import and on every change, studio.lift matches each map against the pattern compilers in reverse. If recompiling with the recovered parameters reproduces the map exactly, it is shown as that pattern. Otherwise it is a custom map with an expert form.

The Studio never rewrites a map just because it opened it. The PoC's mapping-spec.yaml becomes the import/export format for git review, about a third of the Turtle's length.

The mapping pattern catalogue

A pattern is a recurring relational shape with a known R2RML rendering: a detector, a form, a compiler and pattern checks. The catalogue is data, so patterns can be added without changing the Studio or the agent.

Mapping Studio

A workbench page over POST /ops/{op}, with seven views in the order the work is done.

8.1 Connect and profile · 8.2 Scope the ontology

A read-only database registration gives tables sorted by FK in-degree, per-column statistics and value patterns, inferred keys and FKs marked with confidence, and the FK graph clustered into work packages. The mapper then picks the ontology scope (FIBO modules, or classes and their neighbourhood) from the Ontology Repository's module tree. Suggestions come only from the scope; using an outside term widens it explicitly.

  • Rows carry a state: unmapped, suggested, proposed (agent, staged), accepted, ignored (a decision with a reason), gap.
  • Drag a column onto a property to create a correspondence; pick a pattern from the row menu to open its form.
  • "Done" is a choice per column, not 100% coverage: an ignored column counts as covered.

8.4 Entities and IRI policy

A short wizard: base IRI; one EntityDef per root table, proposed from the PK and subclass structure, showing which tables share an identity; three example IRIs from real keys. Templates are typed nowhere else.

8.5 Map editor

The pattern form with pickers restricted to compatible terms; the generated SQL and its first 20 rows; sample triples with provenance and a gained/lost diff; a read-only Turtle view that highlights where each form field lands.

8.7 Tests

A MappingTest is SPARQL plus an expectation: non-empty, a count, rows, or same answer as this SQL, so a data engineer can state the truth in the language they know. Tests run in-process on samples and, when configured, on Ontop over full data. The 237 FIBEN gold queries import as a regression suite.

8.8 Review and history

Each staged map shows its form view, triples diff, findings, affected tests and evidence. Actions: accept, edit and accept (recorded as the reviewer's own commit), reject with reason (becomes a decision). Batch accept only for clean, high-confidence proposals, and logged.

Mapping Authoring Agent

Agent mapping-author, stage populate, machine role agent-mapper: it can stage maps and never validate. Model tasks: mapping.adjudicate and mapping.explain.

ModeTriggerWhat it does
bootstrapnew source, empty mappingfull pipeline, cluster by cluster
extendnew tables or columns in scopepipeline over the unmapped part; existing maps as context
repair-driftschema snapshot diffupdates affected maps; a dropped column is a removal proposal
repair-ontologymapping.impact after a refactoringnew targets for dangling references
fixfindings or failing testsa corrected map, at most two attempts per finding
explaina reviewer opens a proposalplain-language description from the compiled map and three sample triples

  • A2 gate. A decision reaches the model only when the best score is under 0.85 or its margin over the second is under 0.15. Clear structure (subclass tables, join tables) never does. Cost follows ambiguity, not schema size.
  • A3 adjudicate. One table card at a time. The model picks a candidate ID, none, gap or a pattern ID per element. It cannot invent an IRI, a template or SQL; anything else is rejected before compiling.
  • A4 assemble. If no IRI policy exists, the agent proposes one first, and everything else waits for it.
  • A6 submit. In dependency order: IRI policy, entities, links. Gaps go to the ontologist through the ModelingCopilot's path.

Offline simulator

sim_mapping_author takes the top candidate when its score is at least 0.5, none otherwise, and the detected pattern. The whole agent and the review queue run in tests with no model, and the simulator is the baseline a live model must beat.

Scale and learning

150-table schemas run cluster by cluster, each with its own budget and review batch. A live run first reports how many table cards pass the A2 gate and the expected tokens; nothing billed starts without approval. Rejections become hard constraints, accepted choices re-rank similar columns, and the five closest decisions go into the card as examples.

Security, governance and AI use

  • Authorisation is Semantic Turkey's model unchanged: mapper, ontologist, rdfgeek and project manager edit maps; V holders accept staged ones; agent-mapper only stages.
  • Databases are read-only. Logical tables and test SQL must be one SELECT, with a timeout and a row cap.
  • What the model sees is a project policy, mapping.ai_exposure: names (schema and statistics only); profile, the default (plus value patterns, no values); samples (plus up to five top values for low-cardinality columns, with personal-data columns masked). Each model call logs the policy decision.
  • Billing. Live runs need SIP_MODEL and an approved estimate.

Metrics

  • Correspondence precision, recall and F1 per kind.
  • Share of submitted maps with zero errors.
  • Answer equivalence: the 237 FIBEN gold queries under the candidate vs the gold mapping.
  • Reviewer effort: decisions per accepted map; share accepted unedited.
  • Cost: tokens per table; share of decisions sent to the model.

Targets for release R2

  • B1 and B2: F1 ≥ 0.9 with the simulator alone.
  • B2-O: the live agent beats the simulator by ≥ 20 F1 points.
  • B3: recall@1 of FIBO classes ≥ 0.7 on the curated sample, gaps flagged rather than forced.

Open questions

  1. EAV and other unpatterned shapes. Is a pivot pattern needed for target banks, or are custom maps enough?
  2. Named graphs. Add rr:graphMap so each source lands in its own graph for provenance?
  3. Ontop in the release gate. Full-data tests need the Docker sidecar. Gate or advisory?
  4. Decision sharing. Share an accepted "core banking → FIBO" decision set across projects?
  5. Code tables. Individuals or SKOS concepts by default? Proposed: SKOS when the scope has a concept scheme.
